## T1-11 — Filtres persistés + URL shareable

**Objectif** : MonitorsView, IncidentsView, AuditView — les filtres survivent au F5 et sont partageables via URL.

### Design
- Composable `useFilterPreset(key, defaults, options)` dans `frontend/src/composables/useFilterPreset.js`
  - Lit l'état depuis `route.query` d'abord, puis `localStorage[whatisup_filter:{key}]`, sinon `defaults`
  - Sync bidirectionnelle : watch local state → `router.replace({ query })` + `localStorage.setItem`
  - Clé `localStorage` = `whatisup_filter:{viewKey}`
- Serialization simple : objets plats (strings, numbers, bools, arrays de strings). Array en CSV.
- Reset : fonction `reset()` qui wipe localStorage + query params.

### Vues ciblées
- `MonitorsView` — filtres : search, tag_ids, status, group_id
- `IncidentsView` — filtres : statusFilter, daysFilter
- `AuditView` — filtres : actor, resource, action, days (si existant)

### Acceptance
- [ ] F5 garde les filtres
- [ ] URL copiable → autre utilisateur arrive avec le même filtrage
- [ ] Bouton "Clear filters" wipe localStorage + query
- [ ] Tests vitest pour le composable (parse/serialize/reset)

## T1-13 — Timezone utilisateur

**Objectif** : l'UI affiche les dates dans la TZ de l'utilisateur (préférence persistée) + format relatif + absolu en tooltip.

### Backend
- `User.timezone` : `String(64) | None`, default `None` → le client utilise la TZ du navigateur
- Validation côté Pydantic : IANA (liste `zoneinfo.available_timezones()`) ou None
- Migration Alembic (add column nullable)
- Endpoint : exposer dans `UserOut` + ajouter `timezone` à `UserUpdateSelf` ou équivalent
- Tests : set/get/invalid zone rejected

### Frontend
- Composable `useTimezone()` qui retourne la TZ active (user pref, sinon `Intl.DateTimeFormat().resolvedOptions().timeZone`)
- Composant `<FormattedDate :value="iso" :format="'datetime'|'date'|'time'|'relative'" />`
  - `datetime` → format Intl dans la TZ active
  - `relative` → "il y a 3 min" / "dans 2h" via `Intl.RelativeTimeFormat`
  - Tooltip toujours absolu ISO avec TZ en clair
- Settings : SettingsView → section "Préférences" → select `<timezone>` (liste Intl, filtrable)
- Remplacer les `new Date().toLocaleString()` dans :
  - `views/DashboardView.vue` (timestamps cards)
  - `views/MonitorsView.vue` (last_check column)
  - `views/IncidentsView.vue` (started_at, resolved_at, duration)
  - `views/MonitorDetailView.vue` (results table, annotations, incidents, last_heartbeat_at)
  - `components/monitors/MonitorRow.vue` (last_check)
  - `components/monitors/AlertMatrix.vue` (si dates visibles)

### i18n
- `settings.timezone_label`, `settings.timezone_hint`, `settings.timezone_auto`
- `relative.now`, `relative.minutes_ago`, etc. (ou utiliser Intl directement)

### Acceptance
- [ ] User change TZ dans Settings → toutes les dates UI basculent immédiatement
- [ ] Aucune date UTC affichée brute
- [ ] Tooltip d'une date montre l'ISO + nom TZ
- [ ] Backend rejette une TZ invalide (422)
- [ ] Tests server : update self timezone, invalid rejected
- [ ] Tests vitest : FormattedDate render + useTimezone fallback

## Risques / décisions

- **TZ default = null** (navigateur) plutôt que `UTC` : respecte l'attente utilisateur sans config
- **`Intl.RelativeTimeFormat`** au lieu de lib externe (pas de dépendance)
- **Pas de migration des timestamps existants** — tout en UTC en DB, formatage à l'affichage uniquement
- **Ne pas casser tests vitest** — existant utilise parfois des dates fixes ; vérifier
