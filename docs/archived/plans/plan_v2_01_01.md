# V2-01-01 — Auto-traceroute corrélé sur incident

> Foundation de la **vague α** (Pilier 1, Diagnostic Engine).
> Effort prévu : **M** · Statut : ✅ livré 2026-05-01

## Objectif

À l'ouverture d'un incident HTTP/TCP/DNS, déclencher en parallèle depuis chaque sonde affectée une batterie de diagnostics réseau (`traceroute`, `dig +trace`, `openssl s_client`, `ping x5`, `curl -v`) et persister le résultat brut dans `IncidentDiagnostic`. Affichage timeline parallèle dans l'UI.

## Architecture retenue

```
                    ┌────────────────────────┐
                    │ services/incident.py   │
                    │ _open_incident()       │
                    └──────────┬─────────────┘
                               │ enqueue_diagnostic_requests()
                               ▼
        ┌───────────────────────────────────────┐
        │ Redis : whatisup:diag_request:        │
        │   {incident_id}:{probe_id} = JSON spec│
        │ TTL = 1 h                             │
        └──────────┬────────────────────────────┘
                   │
                   ▼ (consommé au prochain heartbeat)
        ┌───────────────────────────────────────┐
        │ probe heartbeat → response includes   │
        │   pending_diagnostics: [...]          │
        └──────────┬────────────────────────────┘
                   │
                   ▼
        ┌───────────────────────────────────────┐
        │ probe.diagnostics.run_collection()    │
        │   asyncio.gather(traceroute, dig,     │
        │     openssl, ping, curl)              │
        └──────────┬────────────────────────────┘
                   │ POST /api/v1/probes/diagnostics
                   ▼
        ┌───────────────────────────────────────┐
        │ IncidentDiagnostic (DB) ←  GET        │
        │ /api/v1/incidents/{id}/diagnostics    │
        └───────────────────────────────────────┘
                   │
                   ▼
        Frontend : section dépliable "Diagnostic"
        sous chaque incident (IncidentsView)
```

**Pourquoi pas pub/sub ?** La trigger-now existante utilise déjà des clés Redis transitoires consommées par le probe au heartbeat suivant — on réutilise le même pattern (cohérence + zéro nouveau composant).

## Contrats

### `IncidentDiagnostic` (modèle)
- `id` UUID PK
- `incident_id` FK incidents (cascade delete)
- `probe_id` FK probes (set null on delete)
- `kind` VARCHAR(20) — `traceroute` | `dig_trace` | `openssl_handshake` | `icmp_ping` | `http_verbose`
- `payload` JSONB — sortie structurée (champs typés par `kind`, voir ci-dessous)
- `error` TEXT NULL — message d'erreur si la collecte a échoué
- `collected_at` DATETIME(tz)
- Index : `(incident_id, kind)` + `(incident_id, probe_id)`

### `payload` par kind
- `traceroute` : `{hops: [{n, host, ip, rtt_ms}], target_ip, total_hops, exit_code, raw}`
- `dig_trace` : `{records: [...], queried_at, exit_code, raw}`
- `openssl_handshake` : `{cn, sans, issuer, valid_from, valid_to, chain_depth, protocol, cipher, exit_code, raw}` — HTTP only
- `icmp_ping` : `{packets_sent, packets_received, loss_pct, rtt_min_ms, rtt_avg_ms, rtt_max_ms, raw}`
- `http_verbose` : `{request_headers, response_headers, status_code, ssl_protocol, exit_code, raw}` — HTTP only

### Heartbeat response (extension)
```json
{
  "monitors": [...],
  "pending_diagnostics": [
    {
      "incident_id": "uuid",
      "monitor_id": "uuid",
      "target": "https://example.com",
      "check_type": "http",
      "kinds": ["traceroute", "dig_trace", "openssl_handshake", "icmp_ping", "http_verbose"]
    }
  ]
}
```

### POST `/api/v1/probes/diagnostics` (ingest)
```json
{
  "incident_id": "uuid",
  "results": [
    {"kind": "traceroute", "payload": {...}, "error": null, "collected_at": "..."},
    ...
  ]
}
```

## Sécurité

- Cible des diagnostics = `monitor.url` (déjà validée au moment de la création monitor — pas de SSRF supplémentaire).
- Ingest endpoint `POST /probes/diagnostics` : auth `get_current_probe` (X-Probe-Api-Key) + filtre `incident_id` ∈ incidents existants.
- GET `/incidents/{id}/diagnostics` : auth `get_current_user` + filtre owner via JOIN monitor (cf. règle CLAUDE.md).
- Rate limit : `30/minute` sur GET, `60/minute` sur POST.
- Subprocess timeouts : 10 s par kind, kill orphelin si dépassé.

## Tests pytest

1. **`test_incident_open_enqueues_diagnostics`** — vérifie que les clés Redis sont posées au moment de `process_check_result` quand un incident s'ouvre.
2. **`test_diagnostic_payload_schema`** — POST `/probes/diagnostics` avec payload valide → 202, ligne en DB ; payload mal formé → 422.
3. **`test_multi_probe_parallel_ingest`** — 3 sondes postent simultanément 3 résultats : tous persistés sans collision FK.
4. **`test_diagnostic_request_consumed_on_heartbeat`** — clé Redis présente → heartbeat la retourne dans `pending_diagnostics` puis la supprime.

## Risques connus

- `mtr --json` indisponible dans `mtr-tiny` (Debian) — fallback sur `traceroute -n` parsé.
- `dig +trace` peut générer 50 lignes — tronquer `raw` à 8 KB pour éviter les payloads obèses.
- Race condition multi-probe : POST concurrents sur même incident — pas d'unique constraint, plusieurs lignes par `(incident, kind, probe)` autorisées (rares cas de retry probe).
